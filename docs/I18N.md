# Interface languages and content conventions

PicoFarm's React application uses i18next and react-i18next with bundled JSON
catalogs. Web and desktop share this frontend. Initial languages are English
(`en`) and Brazilian Portuguese (`pt-BR`). The marketing website, Go API error
payloads and native Wails menus/setup are separate surfaces, not automatically
translated by React catalogs.

## Preference scope

The interface language is a device/browser preference, not a farm-wide database
setting. Choose it in Settings; no server restart, printer reconnect or page
reload should be needed. Saving the language must not alter the configured
currency, database values, printer protocols or customer content. The initial
language follows a supported browser language, with English as fallback. If
browser storage is blocked the selection remains usable for the session.

## Add and maintain translations

Catalogs live under `web/src/i18n/locales/<language>/<namespace>.json`. Namespaces
separate common navigation/settings, production, commerce, fleet, file/material
libraries, shared components and non-React runtime messages. The initialization
module bundles catalogs; no third-party translation service receives UI text,
credentials, file names or customer data.

The current convention is a flat natural-English key, for example:

```tsx
const { t } = useTranslation('production')
t('Delete project “{{name}}”?', { name: project.name })
```

```json
{
  "Delete project “{{name}}”?": "Excluir o projeto “{{name}}”?"
}
```

Keys are case-sensitive; punctuation is significant. `keySeparator` and
`nsSeparator` are disabled, so periods and colons are literal. Keep identical
keys and interpolation variables in each language. Use complete sentences for
interpolated messages rather than concatenating translated fragments. For
count-dependent grammar use i18next plural forms (`_one`, `_other`) and pass a
numeric `count`. Do not use HTML from catalogs or `dangerouslySetInnerHTML`.
React escapes interpolated content.

To add a language, copy the English namespace files, translate their values,
register the locale and native display name in the language configuration, and
extend the supported-language tests. Use native language names rather than
flags (countries and languages are not interchangeable). Review long labels on
narrow screens. Adding right-to-left languages also requires a direction/layout
audit; registering a locale alone is not sufficient.

Never translate transport enums, API paths, query keys, CSS tokens, protocol
commands, brand names, file extensions or user-entered names. Map transport
states to localized display labels. Hooks must observe language changes; avoid
computing translations once at module initialization. Non-React event handlers
can call `i18n.t` at event time. Format dates and numbers with the selected locale
using `Intl`; ISO date inputs and persisted wire formats stay unchanged.

## Validation

```sh
node --test web/tests/*.test.mjs   # or: cd web && npm test
cd web && npm run lint && npm run build
```

Catalog tests check matching keys, nonempty values and interpolation variables,
plus two convention guards: the English value must equal its key, and English
keys must not contain leftover Portuguese UI words (the failure mode where a
Portuguese string became the translation key). Source tests check literal
translation calls against both catalogs and reject raw literal strings in
`alert`/`confirm`/`prompt`, including interpolated template literals. Catalog guards
also reject artificial `(s)` plurals and unreviewed identical English/pt-BR prose;
shared brands, units and external labels have explicit exceptions. These checks
cannot establish translation quality, correct contextual gender/plurals, or
coverage of dynamic strings. Review status maps, generated messages, placeholders,
modal dialogs, toasts, tooltips and screen-reader labels, not only headings.
Backend/provider messages and user content can still appear in their original
language: never blindly replace their words or mutate payloads to hide this.

`node web/scripts/audit-ui-text.mjs [filename-fragment]` lists literal JSX text
and `title`/`placeholder`/`aria-label`/`alt` attributes that are not translation
calls. It is a diagnostic inventory, not a gate: brands, units, URLs and example
values are expected results, and it does not see string literals inside
expressions (status maps, prompt text, error fallbacks, tooltip props). Those
need a separate review pass whenever a page changes.

Notification template presets (Discord/Telegram/webhook bodies and JSON payloads)
are outbound message content stored in the database, not interface copy. They stay
in English so existing automations and payloads are not rewritten by a language
change; only the surrounding labels, descriptions and validation messages are
translated. Desktop notifications use the `runtime` namespace at event time.

Browser-language detection maps every Portuguese variant (`pt`, `pt-PT`,
`pt_BR`, ...) to `pt-BR` and everything else to English. This is a deliberate
approximation until a European Portuguese catalog exists; do not claim pt-PT
support.

Manual acceptance: select each language, navigate all routes, open safe forms,
reload, test keyboard focus, and verify that names, amounts, currency, command
payloads and unsaved drafts do not change. Test blocked localStorage and an
unsupported browser locale. Native desktop startup/setup/tray and actual hardware
operations need separate checks. See [UX review](UX_REVIEW.md).
